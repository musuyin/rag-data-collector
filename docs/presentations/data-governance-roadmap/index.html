01 / positioning

重点不是“下载更多”，
而是让数据可以被信任。

可追溯

每个来源、字段、文件和结论都有 source、quote、locator 或哈希定位。

可复现

成员交付保持只读，机器生成物能够通过统一入口重新构建。

许可可见

未知、非商业、研究限定和不可再分发均保留为风险状态。

项目边界不是通用爬虫，不绕过访问控制，也不把小样本通过解释成全量数据已经验证。
governance before scale
这一页要先把项目的评价标准讲清楚。成功不等于下载量最大，而是任意数据都能回答从哪里来、是否允许使用、有没有被改变、验证做到哪一步。

05 / proof chain

DroneRF 已形成一条真实证据链。

官方 API文件清单 / SHA-256
→
受控下载L/H 两个 RAR
→
原件保全raw / receipt
→
指定抽取segment 0
→
交叉验证哈希完全一致

已经证明

来源、下载文件、指定 segment 和受控样本之间能够建立哈希一致性。

尚未证明

全量 CSV 语义、全部标签、硬件同步、标定和模型效果均未完成逐项验证。

proof ≠ inference
这一页是当前实现最有说服力的案例，同时也要把边界讲完整。验证 segment 0 一致只能证明抽检范围内的文件身份，不能推导整个数据集的语义和标签都已经验证。

06 / target capability

下一阶段：Schema 驱动的
数据治理与导入中间层。

可复用引擎

扫描、计划、分块、批量写入、收据和独立验收形成稳定框架。

ENGINE

一次性任务

每个数据集显式选择 Schema、reader、chunker、transform 和目标表。

JOB + SCHEMA
关键原则不自动猜格式，不自动切模型，不跳过坏文件；未注册能力直接报错。
reusable engine / explicit job contract
目标不是做一个包含大量分支的万能脚本，而是做一个稳定引擎。数据集差异由显式 Schema 和注册处理器表达，任何未声明的情况都应失败并留下证据。

archive separately / index deliberately

08 / data model

两张核心表建立追溯关系。

assets
asset_id确定性 ID source_uri原始对象位置 source_sha256身份校验 license_status使用边界 schema_version导入契约
chunks
chunk_id确定性 ID asset_id原件引用 locator时间 / 帧 / 行 / 偏移 payload_uri载荷位置 transform_version处理版本
chunk_id= SHA256(asset_id + locator + transform + version)
same input + same contract = same identity
首期用 assets 和 chunks 两张表即可表达原件与分块。LanceDB 没有关系数据库式外键约束，因此独立验收程序必须检查所有 chunk 都能找到存在且哈希一致的 asset。

09 / roadmap

先证明契约，再扩大规模。

M5向量检索模型 / 维度 / 索引
M6多模态扩展MMAUD / Anti-UAV300
首个 MVP已经验收的 DroneRF L/H CSV → 显式固定窗口 → assets/chunks → 独立回读验证。
controlled sample before hundreds of GB
开发顺序刻意把 embedding 放在后面。先证明存储、身份、分块、重复运行和追溯都可靠，再决定 RF 特征模型；否则几百 GB 数据可能按照错误语义被批量写入。
